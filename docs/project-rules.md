# 프로젝트 작업 규칙

## 1. 최우선 원칙

1. 이 프로젝트는 인사/수당 산정 시스템이므로 계산 정확성이 가장 중요하다.
2. 화면은 계산 결과를 보여주는 수단일 뿐, 계산 규칙 자체를 숨기거나 임의로 바꾸면 안 된다.
3. 승인 이후의 데이터는 감사 추적이 가능해야 하며, 조용히 덮어쓰면 안 된다.
4. 엑셀과 DB가 동시에 존재할 때 DB를 기준 시스템으로 두되 원본 파일 추적성을 반드시 유지한다.

## 2. 아키텍처 규칙

1. renderer에서 직접 Node API, 파일 시스템, SQLite 드라이버를 호출하지 않는다.
2. 모든 로컬 파일 접근은 `main` 또는 `preload` 브리지를 통해서만 수행한다.
3. 근무시간 계산, 수당 계산, 패턴 시뮬레이션은 UI 컴포넌트 밖의 순수 함수 또는 도메인 서비스로 구현한다.
4. Excel 파서와 Excel 생성기는 양식별 어댑터로 분리한다.
5. 폴더 감시 로직은 UI 라이프사이클에 묶지 않고 앱 서비스로 유지한다.

## 3. 데이터 규칙

1. 날짜 저장 형식은 `YYYY-MM-DD`, 시각 저장 형식은 `HH:mm`을 기본으로 한다.
2. 시간 계산은 자정 넘김, 야간시간대, 휴게시간 차감을 모두 고려한 단일 계산 엔진을 사용한다.
3. 수당 계산은 승인된 실적, 적용 요율, 공휴일 정보, 통상시급을 입력으로 삼아야 한다.
4. 승인 결과는 원본 파일 메타데이터와 함께 저장한다.
5. 시급, 근무지, 근무조, 상태 변경은 모두 이력 테이블을 남긴다.
6. 요율은 연도별 버전 엔터티로 관리하고 직접 하드코딩하지 않는다.

## 4. 계산 규칙 관리

1. 계산식이 바뀌면 코드보다 먼저 문서와 테스트 기대값을 갱신한다.
2. 계산 예제는 최소 문서 예시 3건을 포함하고, 실제 운영 예제까지 확장한다.
3. 반올림/절삭 정책은 계산 엔진에서 일관되게 처리한다.
4. UI에서 표시용 포맷을 위해 원시 계산값을 훼손하지 않는다.

## 5. UI/UX 규칙

1. 모든 사용자 노출 텍스트는 한국어로 작성한다.
2. 전체 테마는 Corporate Blue 기반의 명도 분리형 팔레트를 사용한다.
3. 레이아웃은 좌측 사이드바, 상단 컨텍스트 영역, 우측 메인 데이터 영역 구조를 유지한다.
4. 카드, 테이블, 차트는 동일한 간격 체계와 라운드 규칙을 사용한다.
5. 아이콘은 SVG 세트를 사용하고 이모지는 사용하지 않는다.
6. 차트는 장식이 아니라 의사결정 도구여야 하며, 원본 수치를 함께 확인할 수 있어야 한다.
7. 보라색 위주의 SaaS 감성, 과도한 글로우, 과한 그라디언트는 사용하지 않는다.
8. 상태 표현은 색 하나에만 의존하지 않고 텍스트와 배지를 함께 사용한다.

## 6. 테스트 규칙

1. 도메인 계산 로직은 반드시 자동화 테스트를 작성한다.
2. Excel 파싱은 샘플 파일 기반 회귀 테스트를 둔다.
3. 월 마감 흐름은 최소 1개의 E2E 시나리오로 검증한다.
4. 계산 관련 수정 시 `npm run test`, `npm run typecheck`, `npm run build`를 기본 검증으로 수행한다.

## 7. 보안 및 운영 규칙

1. 로컬 계정 비밀번호는 평문 저장하지 않는다.
2. 실제 사용자 정보가 포함된 샘플 파일은 저장소에 커밋하지 않는다.
3. 설정 파일에는 사용자 PC 절대 경로를 기본값으로 고정하지 않는다.
4. 승인완료 데이터와 원본 파일은 삭제보다 보존을 우선한다.
5. 외부 네트워크 호출은 공휴일 조회 등 허용된 범위로 제한한다.

## 8. 문서화 규칙

1. 기능 개발 전 해당 기능의 입력, 출력, 계산 규칙을 문서로 먼저 정의한다.
2. 근로유형, 요율, 공휴일 정책이 바뀌면 관련 문서를 같은 작업에서 함께 갱신한다.
3. 화면 구조가 바뀌면 UI 브리프와 작업계획서를 함께 검토한다.
4. 운영 규칙이 코드와 다르면 문서를 신뢰하지 말고 즉시 정합성을 맞춘다.

## 9. 작업 프로세스 규칙

1. 3개 이상 파일을 수정할 때는 변경 범위와 의도를 먼저 정리한다.
2. 큰 기능은 "도메인 모델 -> 서비스 -> 저장 -> 화면" 순으로 구현한다.
3. 임시 우회 로직을 넣었다면 제거 시점과 이유를 기록한다.
4. 사용자 요청과 다른 추정이 필요할 때는 추정 내용을 명시하고 진행한다.
5. 이번 초기 반영 이후의 원격 푸시는 항상 새 브랜치에서 진행한다.
6. 커밋 메시지는 `메뉴명.기능` 형식을 사용한다.
