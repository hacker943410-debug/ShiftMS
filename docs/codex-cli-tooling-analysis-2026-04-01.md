## 1. 분석 범위

이 문서는 `Individual_Report.md` 에서 다룬 `GSD`, `ECC`, `UI/UX Pro Max`를 현재 `ShiftMgmt_V3.4` 프로젝트에 지금 설치한다고 가정했을 때의 효과를 평가한다.

동시에, 외부 도구를 추가로 설치하지 않고 현재 시점의 `Codex CLI` 만 사용할 경우 어느 정도의 효율을 낼 수 있는지도 현재 저장소 기준으로 분석한다.

본 문서는 실제 설치 결과가 아니라, 현재 저장소 구조와 로컬 환경을 확인한 뒤 작성한 도입 영향 분석 문서다.

## 2. 현재 프로젝트 기준선

- 문서, 테스트, 빌드, 릴리즈 체크 루틴이 이미 꽤 잘 정리되어 있다.

### 2-4. 현재 기준선의 의미

이 프로젝트는 이미 “맨바닥에서 시작하는 Codex CLI” 상태가 아니다.  
즉, 외부 패키지를 추가하지 않더라도 아래 요소들이 이미 준비되어 있다.

- 코드 탐색용 멀티에이전트 구조
- 테스트/배포/리뷰용 프로젝트 스킬
- 브라우저 검증용 Playwright MCP
- 문서/추론/메모리용 MCP
- Electron 경계가 잘 잡힌 코드 구조

따라서 외부 도구 설치의 순효과는 “없던 기능을 새로 얻는 것”보다 “이미 있는 기능 위에 워크플로우를 더 얹는 것”에 가깝다.

## 3. 도구별 설치 효과

## 3-1. GSD 설치 효과

### 기대 효과

GSD의 핵심 가치는 `.planning/` 중심의 장기 작업 관리와 단계별 실행 흐름 자동화다.  
현재 프로젝트에 설치하면 기능 구현 자체가 갑자기 좋아진다기보다, 큰 작업을 쪼개고 추적하는 방식이 체계화된다.

### 현재 프로젝트에서 유효한 예시

1. `DB업데이트` 기능을 `Access 이관`, `미리보기`, `백업`, `복원`, `검증` 단계로 나눠 장기 작업화할 때 유리하다.
2. `실적 관리`의 재승인/목록 숨김/수당 이력 연결처럼 도메인 규칙이 복잡한 기능을 여러 phase로 쪼개 관리할 때 유리하다.
3. `v0.3.x` 수준의 큰 기능 묶음이 생기면 `ROADMAP`, `STATE`, `SUMMARY` 파일로 작업 맥락을 유지하기 좋다.

### 현재 프로젝트에서 기대할 수 있는 실효

- 단기 패치 작업에서는 효과가 크지 않다.
- 릴리즈 단위 기능 묶음이나 1주 이상 이어지는 멀티태스크 작업에서는 도움이 된다.
- 다만 이 프로젝트는 이미 `project-handbook`, `patch-notes`, `release 문서`, `QA 체크리스트`가 있어서 GSD의 문서 관리 이점이 일부 중복된다.

### 한계와 위험

- `Individual_Report.md` 기준으로 GSD는 Claude 중심 설계라 Codex CLI에서는 직접 효율이 덜 나온다.
- 현재 프로젝트에는 이미 문서 체계가 존재하므로 `.planning/`을 추가하면 문서가 이원화될 수 있다.
- 팀이 GSD 문서를 계속 유지하지 않으면 폴더만 늘고 실익이 줄어든다.

### 현재 프로젝트 적합도

- 적합도: `중간 이하`
- 설치 우선순위: `낮음`
- 권장 방식: `대형 마일스톤 시작 시 프로젝트 로컬에만 제한 도입`

## 4. 현재 시점에서 Codex CLI만 사용할 경우의 효율성 분석

## 4-1. 분석 기준

이 항목은 `외부 패키지(GSD/ECC/UI/UX)`를 추가 설치하지 않은 상태를 뜻한다.  
단, 현재 이 프로젝트와 환경에 이미 존재하는 아래 요소는 포함해서 평가한다.

- `codex-cli 0.117.0`
- `.codex/config.toml`
- 프로젝트 에이전트 설정
- 현재 연결된 MCP
- 현재 저장소의 테스트/빌드/문서/스크립트

즉, “완전한 바닐라 Codex”가 아니라 “현재 프로젝트에서 바로 쓰는 Codex CLI 단독 운영” 기준이다.

## 4-2. Codex CLI가 현재 이미 제공하는 실전 가치

### 강점 1. 코드 탐색과 구현

현재 Codex CLI는 대형 TypeScript 저장소를 탐색하고, 필요한 파일만 읽고, 직접 수정하고, 테스트까지 실행하는 흐름이 이미 매우 강하다.

이 프로젝트에서는 특히 아래 영역에서 효율이 높다.

- `src/main/services` 대형 서비스 수정
- `src/shared/domain` 계산 규칙 검토
- `src/preload` 브리지 경계 확인
- `src/renderer/screens` UI와 도메인 연결 수정

### 강점 2. 회귀 검증

이 프로젝트는 `typecheck`, `test`, `build`, `validate-structure`, smoke 스크립트가 이미 준비돼 있어 Codex CLI가 변경 후 즉시 기준선을 검증하기 좋다.

즉, 툴 자체보다 저장소 품질이 좋아서 Codex CLI 효율이 더 올라간다.

### 강점 3. 멀티에이전트와 역할 분리

현재 프로젝트에는 이미 `explorer`, `builder`, `reviewer`, `debugger`, `tester` 역할이 설정되어 있다.  
이 때문에 큰 작업에서도 탐색, 구현, 리뷰, 테스트를 분리해 돌리기 좋다.

### 강점 4. MCP 확장성

현재 연결된 MCP 조합은 이 프로젝트와 궁합이 좋다.

- `playwright`: UI 검증
- `context7`: 공식 기술 문서 조회
- `sequential_thinking`: 복잡한 판단 정리
- `notion`, `memory`: 외부 지식/기록 연계
- `e2b`: 별도 코드 실행 실험

외부 패키지 없이도 이미 충분히 “연구 + 구현 + 검증” 흐름이 가능하다.

## 4-3. Codex CLI 단독 운영의 약점

### 약점 1. 장기 워크플로우 표준화는 약하다

Codex CLI 자체는 강력한 실행 도구지만, GSD처럼 `.planning/` 중심의 장기 상태 관리 체계를 자동으로 만들어 주지는 않는다.

따라서 여러 주에 걸친 큰 기능 묶음에서는 문서 추적을 사람이 더 신경 써야 한다.

### 약점 2. 디자인 시스템 자동화는 상대적으로 약하다

현 상태에서도 UI 구현은 가능하지만, 화면 철학을 `MASTER.md` 류로 구조화해 일관성 있게 확장하는 전용 장치는 약하다.

### 약점 3. 팀 표준 패턴의 강제력은 제한적이다

Codex CLI는 유연성이 높지만, ECC처럼 규칙과 훅을 강하게 밀어 넣는 패키지에 비하면 팀 전체의 강제 일관성은 낮다.

## 4-5. 해석

현재 프로젝트에서 `Codex CLI만` 사용하더라도 효율은 이미 높은 편이다.  
특히 이 저장소는 테스트와 문서가 잘 갖춰져 있어, 외부 패키지 없이도 `탐색 -> 수정 -> 검증 -> 보고` 흐름이 잘 돌아간다.

실무적으로는 아래처럼 해석하는 것이 맞다.

- 일반 기능 수정, 버그 수정, 테스트 보강, 리뷰: `Codex CLI만으로 충분`
- 대형 마일스톤 관리: `Codex CLI만으로도 가능하지만 별도 워크플로우 도구가 있으면 더 편함`
- 대규모 UI 리브랜딩: `Codex CLI만으로 가능하지만 디자인 전용 체계가 있으면 더 수월함`

## 5. 현재 프로젝트 기준 설치 추천

## 5-1. 결론

현재 시점에서는 `세 도구를 한 번에 모두 설치`하는 것은 권장하지 않는다.

이유는 다음과 같다.

1. 현재 프로젝트는 이미 Codex CLI 기준선이 강하다.
2. 로컬/글로벌 스킬과 MCP가 이미 많아 중복 도입 이득이 생각보다 작다.
3. 외부 도구를 한 번에 많이 얹으면 규칙 충돌과 컨텍스트 혼선이 커질 수 있다.

## 5-2. 추천 우선순위

| 우선순위 | 추천 | 이유 |
|---|---|---|
| 1 | `현재 Codex CLI 유지` | 지금 당장 생산성이 충분히 높다 |
| 2 | `ECC 일부만 선택 도입` | TDD, review, TypeScript 품질 보강에는 현실적인 이득이 있다 |
| 3 | `UI/UX Pro Max 조건부 도입` | 대시보드/운영 화면 재설계 시에만 의미가 크다 |
| 4 | `GSD 보류` | 현재 문서 체계와 일부 중복되며 Codex 직접 효율은 제한적이다 |

## 5-3. 추천 시나리오

### 시나리오 A. 지금처럼 Codex 중심으로 계속 간다

가장 현실적이다.

- 현재 방식 유지
- 필요한 경우 프로젝트 로컬 스킬만 보강
- 릴리즈 문서/패치노트 체계 유지

이 경우 효율 대비 관리 비용이 가장 좋다.

### 시나리오 B. ECC를 소량만 도입한다

현재 프로젝트에서 가장 추천되는 확장 방식이다.

권장 대상:

- TypeScript 규칙
- TDD 흐름
- 리뷰/보안 점검
- 빌드 실패 복구 가이드

비권장 대상:

- 전체 프로필 일괄 설치
- 모든 스킬/룰/훅 전부 활성화

### 시나리오 C. UI/UX Pro Max를 디자인 전용으로만 쓴다

권장 조건:

- 대시보드 구조 전면 재정비
- 운영 관리 화면 정보 구조 개선
- 디자인 시스템 문서화가 필요한 시점

주의:

- 반드시 `project-handbook.md` 기준 색상, 폰트, 업무형 UI 구조를 상위 규칙으로 둬야 한다.

### 시나리오 D. GSD는 대형 기능 시작 시에만 도입한다

추천 대상:

- `DB업데이트` 고도화
- 대규모 Access 이관 자동화
- 여러 주에 걸친 `v0.3.x` 마일스톤

현재 같은 단기 패치 단계에서는 우선순위가 낮다.

## 6. 최종 추천

현재 `ShiftMgmt_V3.4` 기준 최적 전략은 아래와 같다.

1. 기본 운영은 지금처럼 `Codex CLI 중심`으로 간다.
2. 외부 도구를 넣고 싶다면 `ECC 전체`가 아니라 `선별 도입`만 한다.
3. UI/UX 도구는 화면 개편 시점에만 제한적으로 쓴다.
4. GSD는 큰 마일스톤이 열릴 때만 프로젝트 로컬에 도입한다.

한 줄로 요약하면 다음과 같다.

> 현재 프로젝트는 이미 Codex CLI 단독 효율이 높은 편이므로, 지금 당장 필요한 것은 “대규모 추가 설치”보다 “선택적 보강”이다.
