# 운영 관리 실데이터 수동 QA 체크리스트

## 목적
- 자동 smoke로 확인하지 못하는 실제 운영 데이터 기준 검증 항목을 정리한다.
- `공휴일 관리`, `요율 관리`, `사용자 관리`, `양식 관리` 탭을 실제 운영자가 쓰는 순서로 점검한다.
- `release/0.1.0` 분기 전 최종 sign-off 근거 문서로 사용한다.

## 현재 상태
- 2026-03-24 기준 자동 검증은 모두 통과한 상태다.
- 이 문서는 자동 검증을 대체하지 않고, 실제 운영 데이터와 운영 환경 차이를 확인하는 용도로만 사용한다.
- 현재 문서 상태는 `미실행` 이며, 아래 실행 기록을 채운 뒤 결과를 `release-notes-draft-0.1.0.md`, `known-issues.md` 에 반영한다.

## 실행 전 준비
- 최신 코드 기준 `npm run smoke:electron`, `npm run release:check` 가 통과한 상태여야 한다.
- 운영 PC 또는 운영과 동일한 권한 정책을 가진 검수 PC에서 실행한다.
- 아래 경로와 기준 데이터를 준비한다.
  - 승인 대기 폴더
  - 승인 완료 폴더
  - 근무표 내보내기 폴더
  - 품의서 저장 폴더
  - 별첨1 저장 폴더
  - 별첨2 저장 폴더
  - 마이그레이션 파일 경로
    - Access `.accdb` 또는 백업 JSON `.json`
  - 실제 공휴일 API 주소
  - 실제 운영 요율 버전 목록
  - 실제 운영 사용자 목록
  - 실제 사용 중인 근무표/품의서/별첨 양식

## 기록 방법

- 보완 필요 또는 실패면 아래를 함께 남긴다.

## 1. 경로 설정
- [ ] 승인 대기, 승인 완료, 근무표, 품의서, 별첨1, 별첨2 경로가 실제 운영 경로로 저장된다.
- [ ] 마이그레이션 파일 경로는 폴더가 아니라 Access `.accdb` 또는 백업 JSON `.json` 파일을 직접 선택해 저장된다.
- [ ] 앱 재실행 후에도 저장한 경로가 그대로 유지된다.
- [ ] 실적 관리, 수당 관리에서 같은 경로를 다시 조회했을 때 일치한다.
- [ ] 네트워크 드라이브 또는 사내 공유 폴더를 써도 저장과 재조회가 정상이다.
- [ ] `DB업데이트` 실행 전 확인 메시지가 현재 DB 교체 성격과 데이터 초기화 범위를 정확히 안내한다.
- [ ] Access 기준 `DB업데이트` 후 공휴일, 요율, 근무지, 인력, 시급, 패턴, 배정 종료일과 `사업조직별근무실적` 기반 승인/수당 기본 이력이 복원된다.
- [ ] JSON 기준 `DB업데이트` 후 지정한 백업 내용으로 DB가 교체되고, 현재 경로 설정은 유지된다.

## 2. 공휴일 관리
- [ ] 대상 연도를 바꾸면 저장 목록과 API 목록이 해당 연도로 다시 조회된다.
- [ ] 상단 요약 카드의 `같이 있는 날짜 / 저장만 있음 / API만 있음` 수치가 실제 목록과 맞다.
- [ ] 저장 목록과 API 목록 차이가 있을 때 동기화 배너 문구가 맞다.
- [ ] 저장 목록에서 신규 등록한 공휴일이 즉시 반영된다.
- [ ] 저장 목록 공휴일명 수정이 즉시 반영된다.
- [ ] API 목록 항목을 저장 목록으로 반영할 수 있다.
- [ ] 저장 목록 항목을 제거해도 API 원본 목록은 유지된다.
- [ ] `모두 반영` 후 저장 목록이 API 기준으로 교체된다.
- [ ] 실제 운영 연도 기준 공휴일 수가 기존 운영 기준과 맞다.

## 3. 요율 관리
- [ ] 조회 연도를 바꾸면 해당 연도 버전만 다시 보인다.
- [ ] 상단 상태 카드의 `사용중 / 초안 / 종료` 수치가 실제 버전 수와 맞다.
- [ ] 대표 요율 카드가 실제 사용중 버전을 기준으로 보인다.
- [ ] 신규 요율 추가 시 버전명, 적용기간, 상태, 매트릭스 값 저장이 된다.
- [ ] 수정 시 기존 항목이 유지된 채 변경분만 반영된다.
- [ ] 종료된 버전은 이력으로 남고 계산 기준에서 빠진다.
- [ ] 실제 운영에 쓰는 사용중 버전이 수당 계산 기준과 일치한다.
- [ ] 최근 변경 이력의 시각과 버전명이 저장 결과와 맞다.

## 4. 사용자 관리
- [ ] 현재 운영 사용자 목록과 권한/상태가 실제 기준과 맞다.
- [ ] 신규 사용자 추가 시 계정명 중복 검증이 동작한다.
- [ ] 메일주소 형식 검증이 동작한다.
- [ ] 최소 1명 관리자 유지 규칙이 동작한다.
- [ ] 사용자 상태를 `사용중 / 중지 / 대기`로 바꿨을 때 즉시 반영된다.
- [ ] 운영에서 더 이상 쓰지 않는 계정을 삭제할 수 있다.

## 5. 양식 관리
- [ ] 양식이 `근무표 / 품의서 / 별첨1 / 별첨2` 묶음으로 올바르게 보인다.
- [ ] 각 묶음의 건수, 승인 수, 미승인 수, 기본 수가 실제 목록과 맞다.
- [ ] 현재 기본 사용 양식이 운영 기준과 일치한다.
- [ ] 미승인 양식을 승인하면 해당 양식이 사용 가능 목록으로 전환된다.
- [ ] 승인된 양식만 `기본 사용` 전환이 가능하다.
- [ ] 출력 파일명 규칙 변경이 저장되고 실제 출력 파일명에 반영된다.
- [ ] 수정 시 좌표/프로필/설명 값이 기존 운영 기준과 맞게 보존된다.
- [ ] 삭제 불가 조건이 필요한 양식에서 의도치 않은 삭제가 일어나지 않는다.
- [ ] 최근 이력 표의 시각, 종류, 버전, 작업 내용이 실제 작업과 맞다.

## 6. 운영 연계 확인
- [ ] 공휴일 변경이 근무표 배포와 수당 계산 기준에 의도대로 연결된다.
- [ ] 사용중 요율 변경 뒤 새 수당 산출에서 변경분이 반영된다.
- [ ] 기본 사용 양식 변경 뒤 근무표 배포 또는 품의서 출력에서 새 기준이 선택된다.
- [ ] 사용자 상태 변경이 운영자 계정 사용 정책과 충돌하지 않는다.

## 종료 기준
- 모든 항목이 `통과` 또는 명시된 예외와 함께 `보완 필요`로 정리돼 있다.
- `보완 필요` 항목은 별도 수정 목록으로 옮길 수 있을 정도로 재현 정보가 남아 있다.
- 최종 결과를 `docs/release-signoff-checklist.md` 운영 관리 섹션과 연결해 sign-off 한다.
- 최종 결론은 `통과 / 조건부 통과 / 보완 필요 / 실패` 중 하나로 실행 기록에 남긴다.
