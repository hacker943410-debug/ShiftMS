# v0.5.8 구현 분석

## 주요 원인

1. 재분석 마커가 파일별 분석본과 연결되지 않았고 반복 실패 후 해제되어 옛 행이 최신처럼 보일 수 있었다.
2. 같은 시작일 시급 중 최신 행을 삭제하면 정렬상 다음 행이 자동으로 드러나지만 UI와 서비스가 그 변화를 확인하지 않았다.
3. 시급 원본 행 제거와 일반 활동 로그가 분리되어 삭제 전 상태를 원자적으로 보존하지 못했다.
4. 월별 근무표 조회 브리지가 caller 제어 옵션과 전체 직원 객체를 renderer에 노출했다.

## 구현 전략

- 파싱 시작 시 5종 재분석 토큰을 캡처해 파일 행에 저장하고 승인 직전 현재 토큰과 비교한다.
- 읽기/저장 실패 마커를 횟수로 제거하지 않으며, 성공한 파일은 자기 스냅샷으로 개별 통과시킨다.
- 삭제 확인에 대체 시급 ID를 포함하고 main에서 동일 정렬 규칙으로 다시 계산해 불일치를 거절한다.
- `wage_rate_history`에 삭제 전 값을 기록하고 이력·삭제·재분석 마커를 한 트랜잭션으로 묶는다.
- 월별 직원 조회는 main이 역사 인력을 내부 선택하고 `EmployeeScheduleRecord` 최소 DTO만 반환한다.

## 위험 통제

- DB 변경은 기존 시작 시 스키마 보강 경로와 JSON 백업/복원 순서에 포함한다.
- 승인/품의 잠금은 재분석 신선도 관문보다 먼저 확인해 기존 오류 계약을 보존한다.
- 새 의존성은 추가하지 않는다.
